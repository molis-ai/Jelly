# Jelly「拆开并安排」设计

> 日期：2026-08-22
> 状态：设计已确认；工程验证通过；当前设备可覆盖的产品实操通过；真实模型与用户验收待完成
> 分支：`codex/jelly-goalboard-plan-and-schedule`

## 1. 结论

Jelly 第一阶段吸收 GoalBoard 的判断纪律，不接入 GoalBoard 产品或数据。

第一刀叫「拆开并安排」：用户从一篇笔记或一段选中文字开始，Jelly 一次只问一个会改变拆法的问题，给出 2～5 个可独立完成的候选行动。用户可以编辑、删减、排序或只继续拆开某一项。最终确认后，候选行动成为原笔记中的 Task Block；只有用户选择安排的行动才生成 Calendar Item。

这条链路的原则是：

> 系统负责看见可能性，用户负责作决定。

GoalBoard 继续管理工程与承诺的目标真相；Jelly 只管理人怎样把下一步放进一天。第一阶段不新增 Goal、不保存目标树、不连接 GoalBoard 数据库，也不引入目标管理入口。

## 2. 为什么现在做这一刀

Jelly 已有一条真实链路：

```text
Note → Block → Task Block → Calendar Item
```

缺口发生在 Note 与 Task Block 之间。普通用户经常知道“想做什么”，却不知道第一步是什么；直接给一句模糊意图加日期，只会把日历变成压力清单。

「拆开并安排」补的是意图层：先澄清完成意味着什么，再得到可以独立完成的行动，最后才讨论时间。它复用已有 Task Block 与日历关系，不再造任务中心。

如果不做，用户只能自己在笔记中完成拆解；Jelly 仍然能记录和排期，却无法帮助用户从模糊意图走到可开始的行动。

## 3. 目标与非目标

### 3.1 第一阶段目标

- 支持从选中文字或整篇笔记进入。
- 一次只提出一个会改变拆法的问题。
- 初次生成 2～5 个候选行动，每项都有可观察的完成说明。
- 允许直接修改标题、完成说明、顺序和选择状态。
- 允许只重拆指定行动，不覆盖其他修改。
- 确认后的行动成为原笔记中的 Task Block。
- 只为用户选择的行动提议时间；用户确认后才写入日历。
- 智能模型不可用时，仍可诚实地手动拆开并安排。
- 最终写入整单提交、整单撤销，不留下半成品。

### 3.2 明确不做

- 不增加「目标」一级入口。
- 不新增独立 Task、Goal、Outcome 或长期项目实体。
- 不保存拆解树、父子进度、汇总进度或复盘状态。
- 不引入 Claim、Run、Review、Rewire、Policy、Actor 或 MCP。
- 不连接、读取或写入 GoalBoard SQLite。
- 不把父级意图安排进日历。
- 不自动排满一周，不做习惯打卡或 streak。
- 不把灵感自动升级成目标。
- 不在第一阶段同时维护 Apple 本地模型和 Prologue 两条生产调用链。

## 4. 对象与责任边界

| 对象 | 类别 | 真相与生命周期 |
| --- | --- | --- |
| Note / DocumentBlock | 现有持久对象 | 原始意图与上下文；工作台不能偷偷改写 |
| DecompositionSourceSnapshot | 临时来源快照 | 记录 Note、Block、选区、修订和校验值；工作台关闭后丢弃 |
| DecompositionDraft | 临时交互状态 | 问答、候选行动、用户修改、选择与时间建议；最终确认前不持久化 |
| CandidateAction | 临时候选 | 结构在用户确认前不算 Jelly 行动 |
| Task Block | 现有持久行动 | 确认后的行动真相，仍依附原笔记 |
| TaskBlockCalendarLink | 现有持久关系 | 把 Task Block 关联到 Calendar Item |
| Calendar Item | 现有时间投影 | 只承载用户确认过的时间，不拥有拆解或目标真相 |

DecompositionDraft 是一次工作台会话，不是新的领域实体。它不进入 Workspace 数据库，也不在重启后恢复。这样可以保证候选结构不会变成第二套任务真相。

## 5. 入口与完整用户旅程

### 5.1 入口

笔记编辑器提供「拆开并安排」动作：

- 有选区时，入口使用选中文字和所在 Block 作为来源。
- 没有选区时，入口使用整篇笔记。
- 空笔记、只包含空白的选区或无法保存的编辑状态不能进入；Jelly 说明原因并保留编辑焦点。

入口是用户主动触发的上下文动作，不做常驻 AI 提醒，也不在用户写作时自动弹出。

### 5.2 第一步：理解

Jelly 先判断一个问题是否真的会改变拆法。需要澄清时，只显示一个问题，并提供自然语言输入和少量快捷回答。

如果原意已经足够具体，模型可以返回“不需要追问”，直接进入候选行动。系统不能为了展示智能而机械地问问题。

回答只改变临时草稿，不改原文。

### 5.3 第二步：拆开

右侧行动草稿显示 2～5 个初始候选。每项包含：

- 行动标题；
- 完成说明；
- 预计时长；
- 是否保留为行动；
- 是否被用户修改；
- 是否还需要继续拆开。

用户可以：

- 就地修改标题和完成说明；
- 拖动排序；
- 取消选择或删除；
- 新增手工行动；
- 对一项执行「继续拆开」；
- 补充上下文，让尚未锁定的候选重新建议。

用户改过的字段会被锁定。重新生成或补充回答时，模型不得覆盖锁定字段。「继续拆开」只替换目标候选，其余候选的内容、顺序和选择状态保持不变。

### 5.4 第三步：安排

第二步的“确认行动”只冻结当前工作台草稿，不写 Workspace。第三步允许用户单独选择哪些行动进入日历。

每个被选中的行动显示日期、时间和时长建议。用户可以逐项调整，也可以创建全部 Task Block、暂不安排任何日历事项。

最终按钮必须说清楚结果，例如：

- `创建 3 个行动，暂不安排`
- `创建 3 个行动，并安排其中 2 个`

最终确认后才执行一次 Workspace 写入。

### 5.5 完成反馈

成功后关闭工作台，原笔记保持在前景，插入的新 Task Block 可见。顶部显示一句克制反馈，例如“已创建 3 个行动，并安排其中 2 个”，并提供一次性「撤销」。

撤销必须同时移除本次创建的 Task Block、Calendar Item 和 TaskBlockCalendarLink，不影响之后产生的无关修改。

## 6. Task Block 的完成说明

现有 `TaskBlockState` 只有 `completedAt`，无法在行动创建后保留工作台里的“完成长什么样”。第一阶段给它增加一个可选字段：

```swift
public struct TaskBlockState: Codable, Equatable, Sendable {
    public var completedAt: Date?
    public var completionDescription: String?
}
```

约束：

- `completionDescription` 是 Task Block 的次级内容，不是新 Block，也不是子任务。
- 为空或只有空白时规范化为 `nil`。
- 现有和手工新建的普通 Task Block 可以没有完成说明；通过「拆开并安排」创建的 Task Block 必须带非空完成说明。
- 笔记中显示在 Task Block 标题下方，视觉权重低于标题。
- Calendar Item 标题仍只使用 Task Block 的 `inlineContent`，完成说明不进入日历标题。
- Task Block 完成状态联动只关心 `completedAt`，不让完成说明制造第二个完成状态。
- 旧 Workspace 缺少该字段时解码为 `nil`，不要求迁移旧数据。
- Workspace JSON、校验和、备份、撤销和恢复必须保留该字段。
- Jelly Markdown 与 HTML 的往返导入导出必须保留该字段；使用 Jelly 自有的可验证元数据承载，普通外部内容没有该元数据时仍按普通 Task 导入。

这一字段以后可以被轻量目标管理复用，但第一阶段不因此增加父子关系或目标语义。

## 7. 确认后的写回位置

- 从选中文字进入：在选区所在 Block 后插入生成的 Task Block。
- 从整篇笔记进入：在笔记末尾追加生成的 Task Block。
- 原文保持不变；Jelly 不自动插入标题、总结或“AI 生成”标签。
- 多个 Task Block 按用户确认的顺序连续插入。
- 完成说明保存在每个 Task Block 的 `TaskBlockState`，不额外插入容易失去关联的说明段落。

## 8. 拆解引擎架构

### 8.1 Jelly 拥有的窄协议

Jelly 定义一个 App 自有的 `DecompositionPlanning` 边界，只暴露三种能力：

1. 根据来源提出一个关键问题，或说明无需追问；
2. 根据来源和回答生成 2～5 个候选行动；
3. 根据指定候选和最新回答，只重拆这一项。

协议输入只包含本次需要的来源快照、用户回答、候选摘要和锁定字段，不暴露 Workspace Store、写入命令或日历修改能力。

协议输出是候选结构，不是领域命令。适配器不能创建 Task Block、Calendar Item 或修改 Note。

### 8.2 首个真实适配器

第一阶段使用 Apple Foundation Models 的设备端 `SystemLanguageModel` 作为首个生产适配器：

- 使用结构化生成约束问题和 CandidateAction；
- 调用前检查系统模型、设备、地区与当前语言可用性；
- 使用 `#if canImport(FoundationModels)` 和系统可用性保护，保持 Jelly 的 macOS 14 最低系统要求；
- 仅在支持的系统和设备上启用智能生成；
- 不要求用户配置 API Key；
- 不把笔记内容发送给 Jelly 自建网络服务。

官方参考：

- [Foundation Models](https://developer.apple.com/documentation/foundationmodels/)
- [SystemLanguageModel](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel)
- [语言与地区支持](https://developer.apple.com/documentation/foundationmodels/supporting-languages-and-locales-with-foundation-models)

系统模型版本会随操作系统更新。提示词和结构化输出需要按模型版本做真实回归，不能把一次绿测当作永久质量保证。

### 8.3 手动降级

模型不可用、语言不支持、用户取消、请求超时或连续两次输出未通过结构校验时，工作台切换为手动模式：

- 不展示假的 AI 建议；
- 保留原文和用户已输入内容；
- 用户可以手工新增行动、填写完成说明和安排日历；
- 编辑器与其他 Jelly 功能完全不受影响。

手动模式不是 Mock，也不能在产品文案中冒充智能拆解。

### 8.4 Prologue 边界

Prologue 方向上适合成为后续适配器，但当前没有适合 Jelly 的 Swift 原生消费入口。第一阶段不引入 TypeScript/Rust Host，不把这条功能扩大成跨语言 Runtime 接入。

等 Prologue 有稳定、受支持的原生消费边界后，可以新增 `PrologueDecompositionPlanningAdapter`。替换适配器不应改变工作台状态、CandidateAction、Task Block 或 Workspace 写入合同。

## 9. 临时数据结构

### 9.1 DecompositionSourceSnapshot

至少包含：

- `noteID`
- 打开工作台时的 Note revision
- 可选 `sourceBlockID`
- 可选的同 Block 选区范围
- 选中文字或整篇笔记的规范化文本
- 来源校验值

快照只用于模型上下文、插入锚点和最终陈旧检查，不持久化。

### 9.2 CandidateAction

至少包含：

- 本次会话内稳定的 `candidateID`
- `title`
- `completionDescription`
- `estimatedMinutes`，只允许 `15 / 30 / 45 / 60 / 90`
- `selectedForCreation`
- `selectedForCalendar`
- 标题与完成说明各自的用户锁定状态
- 可选的来源候选 ID，用于局部重拆追踪
- 可选的 CalendarProposal

候选 ID 和临时父引用不会写入 Task Block。第一阶段不保存拆解树。

### 9.3 DecompositionDraft

保存：

- 来源快照；
- 当前阶段；
- 问题与用户回答；
- 候选行动及顺序；
- 当前请求 ID 和取消状态；
- 时间建议；
- 最近一次可恢复错误。

工作台关闭后销毁。Jelly 重启后不恢复未确认拆解。

## 10. 时间建议

时间建议由 Jelly 自己的确定性 `CalendarProposalEngine` 负责，不让模型直接修改日历。

输入只使用硬事实：

- 用户选择的行动及顺序；
- 预计时长；
- 当前本地时间；
- 来源中明确出现并经用户确认的截止约束；
- 未来七天已有 Calendar Item。

第一阶段规则：

- 只建议未来七天的本地时间；
- 不与现有 Calendar Item 重叠；
- 默认只在本地时间 09:00～21:00 之间找位置；
- 多个可用位置同等时选择最早的一个；
- 找不到可靠位置时返回“暂无建议”，让用户手动选择；
- 不声称理解用户精力、工作时间或习惯；
- 建议只进入工作台，用户确认前不写日历。

后续若真实使用证明固定时段不够，再单独设计个人可用时段或精力偏好；第一阶段不预建设置系统。

## 11. Workspace 写入与撤销

新增一个原子 Workspace 命令，概念名为 `applyDecompositionPlan`。输入包含：

- 来源 Note 和预期 revision；
- 插入锚点；
- 已确认 Task Block 的完整值与顺序；
- 用户选择安排的 Calendar Item；
- 对应 TaskBlockCalendarLink；
- 预期 Workspace generation；
- 单一 undo label。

提交前必须一次性验证：

- Note 仍存在；
- 插入锚点仍存在；
- Note revision 与来源快照一致；
- 所有新 ID 唯一；
- Task Block 与完成说明合法；
- Calendar Item 合法且没有新冲突；
- 每个关系的 Note、Block 和 Calendar Item 完整对应。

任一验证失败，命令不改变 Workspace。成功后只增加一次 Workspace revision，并产生一条可撤销记录。

撤销遵守 Jelly 现有的精确反向语义：只撤销本次创建的对象与关系；如果之后出现无关修改，不能把无关修改一起回滚。

## 12. 状态、并发与错误处理

### 12.1 模型请求

- 同一阶段只允许一个活动请求。
- 新请求开始前取消旧请求；迟到结果通过请求 ID 丢弃。
- 取消、超时或结构无效不会清空用户输入和手工修改。
- 结构校验失败可进行一次有界修复请求；第二次失败后进入手动模式。
- 输出必须满足数量、非空标题、非空完成说明、合法时长和候选 ID 唯一性。

### 12.2 来源变更

工作台打开期间如果原笔记被修改，最终提交停止，不静默重放。界面显示“这段笔记刚刚被修改，请先确认最新内容”，保留当前草稿供用户查看。

用户可以关闭工作台，或重新载入最新来源后再次确认。Jelly 不自动把旧候选写到未知的新位置。

### 12.3 日历冲突

时间建议生成后如果日历出现新事项，最终提交前重新检查。发生冲突时整单不写入，并把冲突行动带回安排步骤。用户可以重新建议、手动调整或改为只创建行动。

### 12.4 写入失败

Workspace 不可写、保存保护未完成或原子提交失败时，不产生任何 Task Block、Calendar Item 或关系。错误文案必须说明原数据仍保留以及下一步怎么恢复。

## 13. UI 与视觉规范

### 13.1 外层形态

采用居中的临时工作台。原笔记留在半透明背景中，用户可以明确感知来源，但拆解阶段获得足够空间。

工作台不是新一级页面，也不是常驻聊天窗口。关闭后回到原笔记。

### 13.2 内部结构

- 左侧暖灰区域：澄清与补充，只保存本次拆解需要的短对话。
- 右侧白色区域：行动草稿或时间安排，是用户真正操控的对象。
- 底部独立确认区：持续显示当前会创建什么，不让写入动作藏在内容中。
- 顶部使用「理解 / 拆开 / 安排」三段导航，可以返回前一步。

### 13.3 字体与层级

工作台主要使用 12～16 px 的窄字号梯度：

- 功能标题 16 px；
- 分区标题 15 px；
- 正文与行动标题 14 px；
- 完成说明、状态和辅助文案 12 px。

层级主要依靠区域背景、留白、边界、字重和语义颜色，不用悬殊字号制造区分。

### 13.4 操控密度

- 高频操作直接可见：勾选、就地编辑、继续拆开。
- 低频操作放入更多菜单。
- 只有选中某项时才展开标题、完成说明和排序微调工具。
- 模型运行时显示即时、可取消的状态，不用拟人化等待文案制造焦虑。

### 13.5 可访问性与适配

- 所有图标按钮必须有可理解的 VoiceOver 名称和帮助文案。
- 键盘可以完成进入、回答、切换区域、编辑、选择、返回和最终确认。
- 焦点不能因为模型返回或候选刷新跳走。
- 支持深浅主题、减少动态效果和系统字体缩放。
- 较窄窗口改为上下区域，不把正文压成不可读的窄栏。
- 真实长中文标题和完成说明必须验证换行与滚动。

## 14. AI 介入强度

| 时刻 | AI 行为 | 用户控制 |
| --- | --- | --- |
| 用户仍在写笔记 | 不介入 | 无自动提示 |
| 用户主动进入工作台 | 明确检查可用性 | 可关闭或进入手动模式 |
| 理解 | 提出一个关键问题或跳过 | 回答、改写或跳过 |
| 拆开 | 建议候选行动 | 编辑、删除、新增、排序、局部重拆 |
| 安排 | 不直接操作日历 | Jelly 确定性引擎提议，用户逐项确认 |
| 最终写入 | AI 无写权限 | 用户一次明确确认 |

## 15. 验证与验收

### 15.1 工程验证

领域和 App 测试至少覆盖：

- 来源选区与整篇笔记入口；
- 2～5 个初始候选的结构校验；
- 空标题、空完成说明、重复 ID 和非法时长；
- 用户字段锁定；
- 局部重拆只替换目标候选；
- 请求取消、迟到结果和连续无效输出；
- 模型不可用与手动模式；
- TaskBlockState 新字段的 JSON、备份、撤销、Markdown 和 HTML 往返；
- Calendar Item 标题不包含完成说明；
- 时间建议不重叠、未来七天、时区与夏令时；
- 来源陈旧、锚点丢失、日历新增冲突；
- `applyDecompositionPlan` 全有或全无；
- 一次撤销不影响后续无关修改；
- Release 路径不使用 Mock 冒充生产模型；
- 键盘焦点、VoiceOver 名称、深浅主题、减少动态效果和窄窗口布局。

### 15.2 真实模型评测

使用真实 Apple 系统模型和有代表性的中文输入：

- 模糊小事；
- 带截止日期的短任务；
- 已经足够具体、无需追问的行动；
- 较长的个人计划；
- 混有背景、情绪和约束的笔记；
- 可能触发系统安全限制的生活类内容。

硬门槛：

- 结构合法率 100%；
- 不允许父级意图直接进入日历；
- 不允许原文被偷改；
- 不允许用户修改被覆盖；
- 不允许模型输出直接变成 Workspace 写入。

质量评估单独记录：问题是否真的改变拆法、行动是否可独立完成、完成说明是否可观察、预计时长是否基本合理。结构化输出通过不等于建议质量通过。

### 15.3 产品实操

产品实操必须使用最终打包 App、真实中文笔记和已有日历数据，覆盖：

- 智能拆解主流程；
- 无需追问的流程；
- 模型不可用后的手动流程；
- 取消、重试和局部重拆；
- 时间冲突与重新安排；
- 笔记在工作台期间变化；
- 整单撤销；
- 创建后保存、关闭和重启的数据结果；
- 连续处理多篇笔记后的响应与视觉稳定性。

需要直接观察点击后的可见反馈、真实模型等待、长内容布局和连续使用感受。自动点击、Mock、空数据或单元测试不能替代产品实操。

### 15.4 用户验收

用户本人至少使用：

- 一个真实的小事；
- 一个较长、需要继续拆开的想法。

用户判断：问题是否有用、微调是否顺手、时间建议是否制造压力、视觉是否安静清楚。

在用户明确认可前，只能分别报告“工程验证通过”和“产品实操通过”；不能声称用户验收完成。

## 16. 实施顺序

实施计划应保持一个纵向闭环，并按依赖推进：

1. 扩展 Task Block 完成说明及其所有持久化、导入导出与展示路径。
2. 建立纯临时的拆解状态和 Scripted 测试适配器。
3. 建立原子 `applyDecompositionPlan` 与整单撤销。
4. 建立确定性时间建议引擎。
5. 实现工作台三阶段 UI 和手动模式。
6. 接入 Apple Foundation Models 真实适配器与可用性处理。
7. 完成真实模型评测、打包 App 产品实操和用户验收交接。

每一步都必须保持 Jelly 原有笔记、Task Block 与日历主路径可用。Prologue 适配、目标管理和定式不进入本实施计划。
