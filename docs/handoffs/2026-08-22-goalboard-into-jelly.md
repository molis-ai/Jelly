## 3. 两条线不是一回事

| | 定式（8/12） | GoalBoard |
|---|---|---|
| 解决 | 人在还逃得掉的时候开始 | 模糊意图算不算完成、谁卡住、证据够不够、AI 不能偷改目标 |
| 对象 | 过一天的人 | Agent Runtime + 人一起盯工程目标 |
| 失败模式 | 沙发不可逃逸区 | 父级假装可执行、验收不清 |
| 和日历的关系 | 到点只推一个最小动作 | 本身没有时间轴，也不该有 |

都和「拆任务排进日历」有关。把后者整套搬进前者，会把日常记事变成开项目评审：洗个碗之前先澄清 Contract。

## 4. Jelly 缺的是三层，不是第四个模块

现有链路：

```
灵感 / 笔记 → Task Block → 日历事项
```

规格与语义行动层已经写过同一句话：**系统负责看见可能性，用户负责作决定。** 见 [2026-08-12 语义行动层](../product/2026-08-12-semantic-action-layer-direction.md)。

| 层 | 人在干什么 | 现在谁在扛 | 硬塞 GoalBoard 会怎样 |
|---|---|---|---|
| 记录 | 先写下来，越便宜越好 | 灵感、笔记 | 还没写完就要填 outcome / 验收 |
| 意图 | 这件事算完成是什么样，卡在哪，该不该拆 | 几乎没有；最多一篇笔记 | GoalBoard 最强，但也最重 |
| 执行 | 身体在哪个时间真的开始做 | 日历、勾选 | GoalBoard 不懂钟点、精力、沙发不可逃逸区 |

滴答类产品常把意图和执行压成「带日期的复选框」，日历变成愧疚墙。GoalBoard 嵌进来，则容易让意图吃掉记录和执行。

所以不该问「要不要集成 GoalBoard」，该问：**哪一层向谁借能力。**

## 5. 该借 / 不该搬

**该借（纪律，不是产品）：**

- 先问结果，再问活动。叶子必须能独立完成；父级在孩子没齐时不能假装可执行。
- 一次只问一个会改变边界的问题，不要表单式澄清。
- 结构在用户点头之前只是候选，点头之后才写进数据。
- 卡住要能用人话解释，不能只显示灰掉。
- 执行中新发现的事是候选，不是偷偷改目标。

**不该搬：**

- Claim / Run / Review / Rewire / Policy / Actor
- MCP、Runtime 认领、对抗评审
- 第二套 SQLite 真相源
- 「待澄清 / 待执行 / 等待子 Goal」当日常文案
- 第四个一级入口叫「目标」
- 自动排满一周
- 习惯打卡
- 和 GoalBoard 数据库双向同步

GoalBoard 继续管「做 Jelly 这个产品」。Jelly 继续管「过这一天」。Sophon 如果要做，应是会说两种话的助手，不是把 Board 嵌进日历。

## 6. 「拆完落到时间段」为什么不够

用户举例是对的，但漏了三件更致命的事。

**1. 父级不该进日历。**  
「Jelly V1 收尾」不是周四 15:00–16:00 能做完的事。能落钟点的只有叶子：改光标、走灵感、做一次 GUI 验收。GoalBoard 里父级是 `waiting_children`。翻译到 Jelly：父级留在笔记/意图里，只有叶子可以「安排到这周」。

**2. 空档不是仓库货架。**  
GoalBoard 不懂「这人周四晚上已经废了」。不可逃逸区、15 分钟预约、神圣座位，比「把子任务塞进下一个空隙」更接近为什么要做 Jelly。乱填空档 = 看起来勤奋、晚上全违约的日历。

**3. 拆分标准不是工期，是独立结果。**  
GoalBoard 拆的是可独立验收的结果，不是「上午一块、下午一块」。按时间切片拆，会得到一堆无法单独判断完成的碎片。

正确翻译：

```
一篇笔记 / 一句灵感
    →（可选）澄清：完成是什么、卡在哪
    → 拆成可独立完成的叶子
    → 叶子变成 Task Block
    → 只给叶子提议时间，而且要看空档、精力、启动成本
    → 你确认后才写进日历
    → 到点只推一个最小动作，不甩整张清单
```

最后两步来自自制力文章和定式方案，不是来自 GoalBoard。

## 7. 数据上也不该再长一套 Goal

Jelly 已经写明：基础阶段不新增独立 Task；等任务必须脱离单篇笔记、要有父子关系时，再一起设计。现在把 GoalBoard 的 Goal 对象嵌进来，会和 `Task Block ↔ Calendar Item` 抢真相。

更稳的演化：

| 东西 | 怎么放 |
|---|---|
| 短周期、可勾选、可安排 | 继续 Task Block + 日历，不改模型 |
| 仍依附一篇笔记的意图 | 先当这篇笔记的结构，不要新实体 |
| 必须跨笔记、跨周、还要挡住父级被勾完成 | 再引入很轻的 Outcome：结果、子项、是否可执行、卡点。不要 Contract 那一长串 |
| 定式 | **更不该做成 Goal。** 「触发条件 + 最小动作 + 试验期」，挂在灵感或笔记上即可 |

完成打勾可以和日历共用「那天的行动做了」；「目标是否达成」若将来真的连上 GoalBoard，仍以 GoalBoard 验收为准。一篇会议笔记可以挂在日历上，不必先变成 Goal。

## 8. 公司层规划（8/18，规划不是实现）

对外矩阵会话把三种工作拆开，避免连成一张脏网：

| 这是什么 | 谁拥有 | 不该变成 |
|---|---|---|
| 涌进来的活 | Relay | 不是目标，也不是日历 |
| 我要做成的事 | GoalBoard | 不是 Inbox，也不是日程 |
| 落在我一天里的事 | 果冻 / Jelly | 不是 Goal 树，也不是任务中心 |

规划上的健康关系：

```
GoalBoard 管「这件事算不算做成」
果冻管「它落在哪一天、带着哪篇笔记去」
```

一个叶子 Goal 需要出现在本周三下午，才在果冻里生成或关联一个日历事项。

**规划上不该连的（已写死）：**

- GoalBoard 不派单、不选引擎、不变成日历
- 果冻不长出 Goal / 任务中心
- 灵感不要自动变 Goal
- Flyleaf 以后若出现 Goal 界面，只是 GoalBoard 的工作面，不再另建一套目标库
- 果冻灵感 → 笔记 → 日历；只有用户明确说「这是我要长期做成的」才进 GoalBoard

硬事实（8/18 核对过）：**现在没有接上。** GoalBoard 只连了 Codex / Claude；果冻本机可用，不连任何兄弟产品。仓库交叉引用为零。

## 9. 现在不该做 / 以后若做的第一刀

**现在不该做。** 用户在 8/17 当天也没有要求实现，分析完就回去改 UI 了。

若用户以后明确说要做，第一刀不要叫「集成 GoalBoard」，做一个动作就够：

### 「拆开并安排」

1. 选中一篇笔记或一段话
2. 对话里一次只问一个关键问题
3. 给出 2–5 个叶子，每条带「完成长什么样」
4. 可勾选哪些进日历
5. 系统只提议时间，不自动写入
6. 生成 Task Block，可选创建日历事项
7. 一句人话反馈，并能整单撤销

同时仍然不要做：Goal 一级入口、自动排满一周、习惯打卡、Review 流程、和 GoalBoard 数据库双向同步。

### 第二刀才是定式（接 8/12）

一个触发、一个最小动作、「现在做 / 10 分钟后开始」、七天后决定留下、缩小或撤回。没有这一层，拆得再干净也还是会在沙发上停住。

可参考但不要当权威实现的残留：分支 `jelly-sophon`。接盘前先 `git log jelly-sophon --oneline` 看有没有可回收的设计，不要默默合进 main。
